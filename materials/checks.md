# Проверка и демонстрационная программа

## Проверка

Выполняй команды из корня репозитория — папки с README.

~~~bash
python3 checks/acceptance.py            # все задания и бонусы
python3 checks/acceptance.py --task 4   # одно задание
~~~

Проверка вызывает функции из `src/t9.py` с известными входами и сравнивает ответ с ожидаемым. Пункты бывают двух видов:

| Вид | Где | Что показывает при расхождении |
|-----|-----|--------------------------------|
| Открытые | Маленькие примеры и учебный `tiny.txt` | Что ожидалось и что получено |
| С закрытым ответом, пометка «ответ закрыт» | Корпус чатов | Только что получено. Правильный ответ хранится в виде контрольной суммы и не показывается |

Открытые пункты нужны для отладки: их можно пересчитать руками. Закрытые ответы нельзя переписать в код, их можно только посчитать. Если закрытый пункт не сходится, сравни свой результат с маленьким примером, где ожидаемое видно, или посмотри на вывод `demo.py`.

На ревью проверяющий запускает исходную копию проверки в своём режиме. Она добавляет пункты «другие входы»: те же задачи на другом тексте и на других запросах к корпусу чатов. Ответы в них тоже закрыты. Если функции считают по правилам, эти пункты сойдутся сами. Решение, подогнанное под конкретные входы, на них не сойдётся.

Значки в выводе:

| Значок | Что значит |
|--------|------------|
| `+` | Пункт сходится |
| `-` | Не сходится, упал с ошибкой или считался дольше 60 секунд |
| `·` | Функция ещё не написана (`NotImplementedError`) |

Пример расхождения в открытом пункте:

~~~
  -  tokenize: регистр и ё: не сходится
      tokenize("Всё ЕЩЁ тут")
      ожидалось: ['все', 'еще', 'тут']
      получено:  ['всё', 'ещё', 'тут']
~~~

Для длинных списков проверка показывает первое несовпадение. Если один список оказался короче другого, она сообщает об отличии длин.

Пример расхождения в пункте с закрытым ответом:

~~~
  -  сквозной, корпус чатов (нужны задания 1–2): подсказка с откатом (ответ закрыт): не сходится
      predict(["синий", "трамвай"], модель чатов)
      получено:  ['</s>', 'и', 'не']
      правильный ответ в этом пункте закрыт
~~~

Здесь видно, что в подсказку попал маркер `</s>`, хотя правильного ответа проверка не называет.

Если функция упала, в выводе будет тип ошибки, строка в `src/t9.py` и задание, которому принадлежит упавшая функция:

~~~
  -  predict: подсказка с откатом: ошибка KeyError: 'x' (src/t9.py, строка 140, функция top_k, это функция задания 2)
~~~

## Связь заданий в проверке

Функции поздних заданий могут вызывать функции ранних. Поэтому одна ошибка может проявиться сразу в нескольких заданиях. Основные зависимости:

| Задание | Опирается на функции |
|---------|----------------------|
| 2 | `normalize` (задание 1) |
| 3 | `normalize` (1), `top_k` (2) |
| 4 | `normalize` (1), `top_k` (2) |
| Бонус 5 | `normalize` (1), `top_k` (2), `find_context` (4) |
| Бонус 6 | `tokenize`, `normalize` (1), `top_k` (2), `context_for` (4) |

Связи есть и внутри заданий: `tokenize` вызывает `normalize`, `complete` — `top_k`, `find_context` — `context_for`. Под заголовком задания проверка печатает зависимости от других заданий. В твоём решении могут быть и дополнительные связи, если ты используешь свои вспомогательные функции.

Входные данные для проверок на `tiny.txt` — готовые предложения, частоты, пары и модели — готовит сама проверка. Например, тест `next_words` получает правильный словарь пар, даже если твоя `count_pairs` пока работает неверно. Сквозные пункты на корпусе чатов, напротив, собирают данные твоими функциями.

Пометка «нужно задание N» отмечает зависимость, которую авторы проверки выделили явно. **Пометки не перечисляют все зависимости** и на оценку не влияют: они только подсказывают, где ещё искать причину.

### Как проверка ищет причину

Если пункт не сошёлся, проверка разбирает его сама:

- повторяет пункт с правильными версиями функций, которые он вызывает не напрямую: `normalize`, `top_k`, `context_for`, `count_words`, `count_pairs`, `count_ngrams`, `build_model`. Если с ними пункт сходится, причина в подставленной функции;
- для сквозных пунктов на корпусе чатов сверяет предложения, которые вернула твоя `read_sentences`. Если они неправильные, повторяет пункт на правильных предложениях. Сходится — причина в задании 1. Не сходится — ошибка есть и в функциях этого пункта, и он учитывается.

Пункт не идёт в оценку, только если ошибка уже учтена в собственных пунктах той функции — тех, что вызывают её напрямую. Так выглядит такой пункт:

~~~
  -  next_words: регистр и ё (нужно задание 1: normalize): не сходится
      next_words("Пёс", пары tiny.txt)
      ожидалось: ['бежит', 'ест', 'любит']
      получено:  ['сидит', 'любит', 'ест']
      в оценку не идёт: с правильной top_k (задание 2) пункт сходится; ошибка учтена в собственных пунктах top_k
~~~

Начни исправление с функции, которая названа в этой строке.

Бывает, что пункт учитывается, хотя причина найдена. Тогда вместо «в оценку не идёт» проверка пишет строку «причина»:

- функция-причина из того же задания ещё не написана. Ненаписанная функция — это невыполненная часть задания, а не ошибка в другом месте;
- собственные пункты функции-причины сходятся. Тогда ошибка не учтена больше нигде и учитывается там, где проявилась.

Если правильной версии функции в проверке нет (`tokenize`, `find_context`, `predict`, функции бонусов), пункт учитывается там, где не сошёлся. Например, бонус, который не работает из-за ошибки в `find_context`, теряет свои пункты.

### «Для оценки» и баллы на P2P

В итоге задания и в сводке у каждого задания есть «для оценки: a из b»: пункты задания без тех, что не идут в оценку. По этой цифре проверяющий ставит баллы, вручную пункты не исключаются:

~~~
  Задание 2. Частоты и дописывание слова: FAIL (5/9); для оценки: 5 из 6
  Задание 3. Пары слов: FAIL (5/9); для оценки: 5 из 5
~~~

Здесь одна ошибка в `top_k` уронила пункты обоих заданий, но снижает только оценку задания 2: не сошёлся собственный пункт `top_k`.

Объяснение своего кода оценивается отдельно от совпадения ответов.

## Итог проверки

В конце проверка печатает сводку и строку `Итог: PASS` или `Итог: FAIL`. Итог `PASS` получается, когда одновременно:

- все пункты обязательных заданий 1–4 сходятся;
- в `src/` нет сторонних библиотек — строка «Только стандартная библиотека: PASS»;
- выданные корпуса `datasets/tiny.txt`, `datasets/chats_2000.txt` и `demo.py` не изменены — строка «Выданные файлы не изменены: PASS».
- файл правильных предложений `checks/chats_2000_sentences.dat` на месте и цел — строка «Файлы проверки на месте: PASS».

Если «Файлы проверки на месте: FAIL», восстанови выданную папку `checks/` из ветки `master` и повтори запуск. Без неё итог — `FAIL`, даже если функции работают правильно. На ревью проверяющий восстанавливает файлы своей копии проверки; это не ошибка решения участника.

Бонусы печатаются в сводке, но на общий итог не влияют. При `--task N` итог считается по выбранному заданию, включая бонус, а требования к библиотекам и целостности выданных файлов сохраняются.

Если в `src/t9.py` синтаксическая ошибка или файл падает при загрузке, проверка покажет строку и текст ошибки и не проверит ни одно задание. В сводке у всех заданий будет «не проверено», итог — `FAIL`. То же будет, если вне функций выполняется код, который ждёт ввода или не заканчивается. Такой код ставят под `if __name__ == "__main__":`. Демонстрационная программа в этих случаях тоже не запустится.

## Демонстрационная программа

`demo.py` вызывает твои функции на выбранном корпусе и показывает результат. В зависимости от команды она считает частоты, пары или собирает модель. Ожидаемые ответы программа не сравнивает: для этого нужна автопроверка.

Во всех командах ниже основной корпус указан явно: `--corpus datasets/chats_2000.txt`. Он же используется, если параметр не указан.

| Команда | Что показывает | Нужно задание |
|---------|----------------|---------------|
| `python3 demo.py words --corpus datasets/chats_2000.txt` | Самые частые слова | 1, 2 |
| `python3 demo.py complete при --corpus datasets/chats_2000.txt --k 3` | Дописывание слова | 1, 2 |
| `python3 demo.py next можешь --corpus datasets/chats_2000.txt --k 3` | Следующее слово по одному слову | 1–3 |
| `python3 demo.py predict "можешь прислать" --corpus datasets/chats_2000.txt --k 3` | Подсказка с откатом и найденный контекст | 1, 2, 4 |
| `python3 demo.py greedy я --corpus datasets/chats_2000.txt` | Жадная генерация | 1, 2, 4, бонус 5 |
| `python3 demo.py random я --corpus datasets/chats_2000.txt --seed 7` | Случайная генерация | 1, 2, 4, бонус 5 |
| `python3 demo.py suggest "можешь при" --corpus datasets/chats_2000.txt --k 3` | Подсказка по набранному тексту | 1, 2, 4, бонус 6 |

Числа в скобках — частоты из твоих подсчётов:

- у `complete` — сколько раз слово встретилось в корпусе;
- у `next` — сколько раз слово шло после введённого;
- у `predict` — сколько раз слово шло после найденного контекста.

Для найденного контекста `predict` ещё печатает, сколько за ним примеров и вариантов продолжения и сколько раз после него заканчивалось предложение.

Параметры:

- `--corpus ПУТЬ` — на каком тексте учить модель: `datasets/chats_2000.txt`, `datasets/tiny.txt` или свой;
- `--n 2` — пример выбора наибольшей длины n-граммы; без параметра используется 3;
- `--k 3` — показать до трёх подсказок; без параметра используется 5;
- `--seed 5` — seed для `random`;
- `--words 40` — добавить не больше 40 слов при генерации; начальные слова в лимит не входят. Выбор `</s>` может остановить генерацию раньше.

## Как вызвать одну функцию вручную

~~~bash
python3 -c "from src.t9 import tokenize; print(tokenize('По-моему - нет'))"
~~~

Или в интерактивном Python из корня репозитория:

~~~
$ python3
>>> from src.t9 import *
>>> s = read_sentences("datasets/tiny.txt")
>>> pairs = count_pairs(s)
>>> pairs["кот"]
~~~

Чтобы изменения в `src/t9.py` подхватились, выйди из интерактивного Python (Ctrl+D) и зайди снова.
